Executive Summary

The LogixPulse Platform is an enterprise-grade, dual-portal web application architected to bridge internal business development operations and external client onboarding workflows into a cohesive, secure ecosystem. Developed during Sprint 1 (Weeks 7 and 8) of the DevLogix Strategic Internship Program (SIP'26) Engineering Track (PHP Practice), Module 1 establishes the operational core of the platform: CRM & Client Onboarding.

Historically, enterprise sales teams and onboarding operations suffered from fragmented tooling—leads were tracked in disparate spreadsheets, client contracts required third-party signature tools, and financial documentation was communicated over insecure email channels. LogixPulse eliminates these frictions through two synchronized portals governed by a unified database:

Dual-Portal Architectural Paradigm
1. Internal CRM & Executive Portal
Multi-column visual Kanban board, HTML5 drag-and-drop pipeline progression, debounced multi-field search, real-time KPI stat cards, pipeline velocity metrics, live cross-lead activity feed, and team leaderboard with quota attainment.
2. Unified Core Engine
PHP 8.0+ native session router, centralized PDO singleton with dual-schema compatibility, transactional persistence, bcrypt password hashing, and script-execution-hardened file vaults.
3. External Client Onboarding Portal
Slack-style passwordless 6-digit OTP magic code authentication, self-service password reset, real-time onboarding progression timeline, Master Service Agreement with HTML5 Canvas digital signature pad, and client-isolated invoice downloads.

3. User Classes, Personas & Role-Based Access Control (RBAC)

3.1 User Class Descriptions

LogixPulse enforces strict Role-Based Access Control (RBAC). A user's identity is authenticated server-side and maintained in the native PHP session array ($_SESSION['user_id'], $_SESSION['role']). The system recognizes five operational personas:

  1. System Administrator (admin): Superuser responsible for platform governance. Has unrestricted privileges across all CRM leads, internal user management, invoice uploading, and deletion actions.
  2. Strategic Executive (executive): Executive stakeholder requiring read-only macro visibility into business development performance, revenue velocity, KPI cards, and cross-team activity feeds.
  3. Practice Head (head): Engineering or sales leader supervising squads and pipeline velocity. Can view, manage, and assign leads across all territories.
  4. Business Development Representative (team / staff / user): Frontline sales agent. Manages assigned leads, executes stage transitions on the Kanban board, adds manual communication notes, and tracks individual quota attainment.
  5. Client (client): External commercial partner. Restricted exclusively to the Client Onboarding Portal. Can review project milestones, download personal invoices, and execute legal agreements.

4. System Features & Functional Requirements

4.1 Subsystem 1: Dual-Portal Authentication & Identity Governance

FR-AUTH-01 Traditional Credential Authentication All Users
Description: Authenticate users using corporate email and plaintext password validated against native Bcrypt cryptographic hashes stored in the users table.
Trigger: User submits traditional login form on index.html or backend/internal_login.php.
Flow of Events:
  1. Browser sends POST /api/login.php with email and password.
  2. Backend sanitizes inputs and executes parameterized query: SELECT * FROM users WHERE email = ? LIMIT 1.
  3. If user exists, backend evaluates password using password_verify($password, $user['password_hash']).
  4. On success: calls session_regenerate_id(true), initializes $_SESSION['user_id'], $_SESSION['email'], $_SESSION['role'].
  5. Returns JSON: {"error": false, "role": "client", "redirect": "client-portal-dashboard/index.php"}.
  6. On failure: returns HTTP 401 with JSON: {"error": true, "message": "Invalid email or password"}.
Done When: Postman and browser testing with valid credentials returns successful session and correct role; testing with invalid credentials returns "login failed" without exposing database errors or stack traces.
FR-AUTH-02 Passwordless Magic Code (OTP) Authentication Client Only
Description: Enables Slack-style passwordless authentication. A client enters their registered email, receives a cryptographically generated 6-digit numeric OTP valid for 10 minutes, and authenticates by submitting the code.
Endpoints: POST /api/request_magic_code.php, POST /api/verify_magic_code.php.
Business Rules:
  • Code must be exactly 6 random digits generated via random_int(100000, 999999).
  • Expiration period: exactly 10 minutes (NOW() + INTERVAL '10 MINUTE').
  • Brute-force protection: each code record tracks attempts. If attempts exceed 5, the code is invalidated.
  • Replay protection: once verified, used_at is set to the current timestamp. Single-use only.
Done When: Client requests code → code is saved in magic_codes → submitting code within 10 minutes logs client in → submitting expired code, wrong code, or already-used code rejects with specific error message.
FR-AUTH-03 Self-Service Password Reset Flow All Users
Description: Two-step password recovery allowing users to reset their forgotten password via secure cryptographic token.
Endpoints: POST /api/request_password_reset.php, POST /api/reset_password.php.
Flow of Events:
  1. User enters email on reset-password.html.
  2. Backend generates 64-character random hex token via bin2hex(random_bytes(32)), computes SHA-256 hash (hash('sha256', $token)), and stores hash in password_resets with 1-hour expiration.
  3. User navigates to set-new-password.html?token=... and submits new password (minimum 8 characters).
  4. Backend hashes input with password_hash($newPassword, PASSWORD_DEFAULT), updates users.password_hash, and marks token as used.
Done When: User can complete reset flow → immediately log in with new password → old password no longer works → token cannot be reused.
FR-AUTH-04 Session Identity Verification & Router System Wide
Description: Provides heartbeat identity checks and automated traffic routing based on active session role.
Behaviors:
  • GET /index.php: If unauthenticated, serves/redirects to index.html. If authenticated as client, redirects to client-portal-dashboard/index.php. If authenticated as admin/staff, redirects to backend/main_dashboard.php.
  • GET /api/who_is_logged_in.php: Returns active session user metadata: {"logged_in": true, "user_id": 1, "role": "admin", "email": "admin@logixpulse.com"}.
  • GET /logout.php: Calls session_destroy(), unsets $_SESSION, purges session cookies, and redirects to index.html.
Done When: Opening the root domain correctly routes users according to their active session; logging out fully terminates session state across both portals.

4.2 Subsystem 2: Internal CRM Pipeline & Kanban Management

FR-CRM-01 Multi-Column Visual Kanban Board Staff / BD / Admin
Description: Displays all active commercial leads partitioned into exactly four horizontal pipeline columns: New, Contacted, Meeting Booked, and Closed.
Data Integration: On page initialization, queries GET /api/grouped-leads.php. The backend invokes LeadRepository::getGroupedLeads() to retrieve all leads grouped by status/stage.
Card Metadata: Each lead card displays: Lead Name, Company, Primary Email, Phone Number, Source Tag (e.g., Inbound, LinkedIn, Referral), and Assigned Representative avatar.
Done When: All four columns render side-by-side with equal proportional width; live database leads populate their respective columns without layout corruption across screen resizes.
FR-CRM-02 Interactive Drag-and-Drop Stage Transitions Staff / BD / Admin
Description: Users can click and drag any lead card from its current column and drop it into a target column using the native HTML5 Drag and Drop API.
Client-Side Implementation: Cards specify draggable="true" with event listeners for dragstart, dragover, dragleave, and drop. Ghost previews and hover column highlights provide visual feedback.
Persistence Synchronization: Upon drop, frontend immediately dispatches POST /api/update_lead_stage.php containing lead_id and new_stage. If the API returns success, a toast confirmation appears. If the API fails, the card reverts to its origin column with an error toast.
Done When: Dragging a card to a new column moves it visually, persists to the database, and the new position survives a complete browser hard refresh.
FR-CRM-03 Atomic Stage Update & Transactional Audit Logging Backend Engine
Description: Backend processor for stage changes enforcing database transaction integrity.
Endpoint: POST /api/update_lead_stage.php.
Execution Logic: 
$pdo->beginTransaction();
// 1. Dual-column compatibility update
$stmt = $pdo->prepare("UPDATE leads SET status = ?, stage = ?, updated_at = NOW() WHERE id = ?");
$stmt->execute([$newStage, $newStage, $leadId]);

// 2. Automated audit log insertion
$logStmt = $pdo->prepare("INSERT INTO activity_logs (lead_id, user_id, action, activity_type, description, note, created_by)
                         VALUES (?, ?, 'stage_change', 'stage_change', ?, ?, ?)");
$desc = "Moved from {$oldStage} to {$newStage}";
$logStmt->execute([$leadId, $_SESSION['user_id'], $desc, $desc, $_SESSION['name']]);
$pdo->commit();
Done When: Executing a stage change modifies both status and stage columns in leads AND creates a corresponding entry in activity_logs within a single atomic commit.
FR-CRM-04 Add Lead Modal & Server-Side Validation Staff / BD / Admin
Description: Modal form allowing BD representatives to capture new inbound prospects directly onto the CRM board.
Input Fields: Full Name (required), Email Address (required, valid email syntax), Phone Number (required), Acquisition Source (select: Website, LinkedIn, Referral, Cold Outreach).
Server-Side Validation: POST /api/save_lead.php validates that required fields are non-empty and verifies email structure with filter_var($email, FILTER_VALIDATE_EMAIL). Rejects invalid submissions with HTTP 422.
Board Insertion: Upon successful insert, returns newly created lead JSON. Frontend dynamically injects the card into the New column without reloading the page.
Done When: Submitting valid lead details creates record in leads, logs creation in activity_logs, and card instantly appears in the New column; invalid email formats are rejected with a clear error toast.
FR-CRM-05 Debounced Multi-Column Lead Search Staff / BD / Admin
Description: Real-time search bar embedded in the CRM board header that filters displayed leads as the user types.
Query Logic: Client debounces input by 300ms, then invokes GET /api/lead_search.php?search={query}. The backend executes parameterized SQL with wildcards: SELECT * FROM leads WHERE name LIKE ? OR email LIKE ? OR phone LIKE ? OR company LIKE ?.
Edge Cases: Submitting an empty query returns all active leads. If zero matches are found, columns display an empty-state message: "No matching leads found."
Done When: Typing partial strings (e.g., "Ah" for "Ahmed") immediately narrows board cards to matching records across name, email, or company; clearing the search restores the full board.
FR-CRM-06 Lead Profile & Details Sliding Drawer Staff / BD / Admin
Description: Clicking any lead card triggers an animated offcanvas slide-over drawer displaying full customer information, current stage badge, acquisition metadata, and complete historical audit trail.
Data Endpoints: GET /api/lead_details.php?id={id} for profile attributes and GET /api/lead_activity.php?lead_id={id} for audit history.
Done When: Clicking different cards dynamically populates the drawer with the exact attributes and timeline of the selected lead, with zero cross-lead data bleed.
FR-CRM-07 Administrative Lead Deletion with Two-Step Confirmation Admin Only
Description: Protects the database from accidental lead loss. Only users with role admin can delete a lead. Triggering delete presents a modal confirmation: "Are you sure you want to permanently delete this lead? This action cannot be undone."
Security Check: POST /api/leads_delete.php checks $_SESSION['role'] === 'admin'. Rejects any non-admin role with HTTP 403 Forbidden.
Done When: Admin can delete lead after confirming modal → card vanishes from board → non-admin users attempting delete are rejected with "Not allowed".

4.5 Subsystem 5: External Client Portal & Onboarding Progression

FR-CLT-01 Interactive Client Onboarding Milestone Timeline Client Only
Description: Visual step-by-step progress timeline displaying the client's current onboarding lifecycle stage (e.g., Discovery → Agreement Signed → Technical Architecture → Development → Delivery).
Data Schema: Driven by tables client_timeline_progress and timeline_steps.
Dynamic State Resolution: Backend function getClientTimeline($clientId) evaluates each step against current_step_order:
  • step_order < current_step_order → Status = Completed (green checkmark, clickable).
  • step_order == current_step_order → Status = Current / In Progress (pulsating active blue badge).
  • step_order > current_step_order → Status = Upcoming / Pending (muted gray icon, disabled).
Security & Isolation: $clientId is pulled strictly from $_SESSION['user_id']. Client A can never view Client B's progress.
Done When: Logging in as two distinct sample clients displays two distinct onboarding phases matching database seed rows; unauthenticated access displays an invitation to log in.
FR-CLT-02 Client Engagement Overview & Active Projects Client Only
Description: Dashboard summary cards presenting active commercial projects, assigned account manager contact information, and primary engagement deliverables.
Data Source: Evaluates projects table where projects.client_id = $_SESSION['user_id'].
Done When: The client dashboard accurately reflects projects assigned to the logged-in user without cross-tenant leakage.

5. External Interface Specifications & REST API Dictionary

5.1 Communication Protocols & General Conventions

LogixPulse APIs adhere to RESTful conventions communicating over standard HTTP/HTTPS. Unless otherwise specified (e.g., binary PDF streaming or multi-part uploads), all endpoints accept and return JSON payloads formatted with standard HTTP response status codes:

  • 200 OK: Request completed successfully.
  • 400 Bad Request: Missing required fields or malformed payload.
  • 401 Unauthorized: Missing or expired session; user must authenticate.
  • 403 Forbidden: Authenticated user lacks RBAC role permissions for this resource.
  • 404 Not Found: Specified entity (lead, invoice, user) does not exist.
  • 422 Unprocessable Entity: Validation failed (e.g., invalid email syntax).
  • 500 Internal Server Error: Caught backend exception. Always returns clean JSON: {"error": true, "message": "Database error occurred"}.

7. Non-Functional Requirements (NFRs)

7.1 Security Requirements & OWASP ASVS Mitigation Matrix

OWASP Threat Category LogixPulse Architectural Vulnerability Risk Mandatory Engineering Defense & Verification Rule
A01: Broken Access Control (BOLA / IDOR) Client manipulates URL parameter (download.php?id=2) to access another company's financial invoice or timeline. Tenant identity MUST be extracted strictly from $_SESSION['user_id']. Database queries verify invoices.client_id == $_SESSION['user_id']. Violations immediately terminate with HTTP 403.
A02: Cryptographic Failures Storage of plaintext passwords or weak MD5/SHA1 hashes susceptible to rainbow table breaches. Passwords MUST be hashed using PHP's native password_hash($pwd, PASSWORD_DEFAULT) (Bcrypt) and verified via password_verify(). Demo seed scripts must contain pre-computed verified hashes.
A03: Injection (SQL Injection) User input injected into search strings or stage updates altering query semantics. 100% of SQL executions MUST use PDO parameterized prepared statements ($pdo->prepare() and $stmt->execute([$...])). Zero string concatenation ("SELECT ... " . $input) permitted in codebase.
A04: Insecure Design & RCE Malicious actor uploads shell.php disguised as an invoice to execute code on the server. Uploads directory is shielded with .htaccess disabling script execution. Invoices are validated via finfo_file() for true application/pdf MIME, and stored under randomized UUID filenames.
A07: Identification & Auth Failures Session fixation or brute forcing of 6-digit magic codes. Calls session_regenerate_id(true) upon every authentication event. Magic codes expire in 10 minutes and lock after 5 failed attempts. Single-use enforcement via used_at timestamp.

7.2 Performance & Scalability Requirements

  • API Response Latency: 95% of API requests (excluding binary file downloads) MUST return in under 200 milliseconds under nominal load (50 concurrent users).
  • Kanban Drag Responsiveness: Client-side UI must transition the dragged card instantly (<16ms frame budget), executing the background persistence request asynchronously.
  • Database Indexing: Compound indexes on (lead_id, created_at, id) in activity_logs and client_id in invoices guarantee sub-10ms lookup times even as tables scale past 50,000 records.
  • Database Connection Management: The application implements a singleton connection pattern in config/database.php, ensuring exactly one PDO connection per HTTP request lifecycle.

7.3 Usability, Accessibility & Responsive Layout Standards

  • Design Fidelity: Frontend implementations by Squads FE-A and FE-B MUST conform precisely to the pre-approved LogixPulse design system tokens, typography scales, and component layouts.
  • Mobile Viewport Support: All screens must remain fully functional and visually unbroken on mobile screens down to 320px width. Specifically:
    • Kanban columns gracefully stack or provide horizontal scrolling.
    • HTML5 Canvas signature pad adjusts dynamically to available screen width without clipping drawing strokes.
    • Data tables (Invoices, Leaderboard) provide responsive card transformations or clean horizontal scrolling.
  • Real-Time Visual Feedback: Every asynchronous action lasting >300ms must display a loading spinner. Every mutation must trigger a color-coded toast notification (Green for success, Red for failure).

7.4 Maintainability, Code Quality & Clean Architecture

  • Zero Unhandled Fatal Errors: All database and file I/O operations must be wrapped in try/catch blocks. Under no circumstances may raw PHP call stacks or fatal errors be exposed to the client.
  • Strict exit; Termination: Every API endpoint MUST invoke exit; or die() immediately following an error JSON response to prevent PHP from executing subsequent code blocks.
  • Single Source of Truth: Database configuration must reside exclusively in config/database.php reading from environment variables (.env). Legacy configuration scripts act as thin wrappers forwarding to this unified singleton.
